# Site merges take turns per geohash4 cell in the worker; the worker stays at one replica

Context: on demo, two of the four same-spot duplicate groups were founded 3 s and 5 s apart, 3.4 m and 2.8 m from each other. Phones on 3G flush their outboxes together, `SqsQueuePoller` handles a batch with `Promise.all`, and both reports picked no site and founded one. The pick reads the `by-geohash` GSI, which is eventually consistent, so even one after the other a site founded a moment ago can be missed.

Decision:
- `SiteMerger` holds a `MergeLock` (port) on the geohash4 cells of the report's merge area for "pick a site, or found one" only. Moderation, blur, ml, brands and location stay parallel. `InProcessMergeLock` keeps one first-come queue per cell and takes cells in sorted order, so reports in other cells run side by side and no two holders wait on each other.
- The worker's merger reads sites through `RecentSitesRepository`: a site it founded is read by id as a candidate until the index returns it.
- Both are in-process. The worker stays at `replicas: 1` (infra/k8s/base/worker.yaml says why); more replicas need a shared lock first, for example a conditional DynamoDB lock item per cell.
- No contract change; contracts/README.md says this in text.

Consequences for other lanes: infra must not scale the worker past one replica without the shared lock, and the worker Deployment uses `strategy: Recreate`, so a rollout never runs two worker pods at once (SQS keeps the messages meanwhile). Merges in one city take turns, a few hundred milliseconds each, well inside the 240 s message deadline. Duplicates founded before this stay until the listing script's groups are merged.

Rejected alternatives: one global mutex (simpler, but blocks other cities for nothing); a DynamoDB lock item now (a new table key or item shape, not needed for one replica); waiting a fixed time for the index (slow and still not certain).
